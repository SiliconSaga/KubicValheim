# Running several instances

Instances are **data-driven**: one namespace per instance, rendered from the shared base. There is no copy-paste step, and no per-instance fork of the manifests.

```bash
scripts/start-server.sh asgard 32556 Asgard           # render kustomize/overlays/asgard (ns valheim-asgard)
APPLY=1 scripts/start-server.sh asgard 32556 Asgard   # render and apply
```

The three arguments are the instance slug, its game NodePort, and the world name. The query port is the game port plus one, so `32556` game implies `32557` query — allow both through the firewall.

## Choosing a port

Every instance needs its own NodePort pair, because they all share the node addresses. The generator reserves `gamePort + 1` for queries, so check **both** ports of the pair you are about to claim against **both** ports of every existing instance — a new game port of `32556` collides with an existing instance's query port of `32556` just as surely as with its game port.

## The world name matters

The third argument sets `WORLD` in the instance's `instance-patch.yaml`, and Valheim loads whatever that names. This is the value that has to match when restoring an existing world onto a new instance — see [world-identity.md](world-identity.md) before reviving an old save.

## Secrets

The rendered overlay's `secret.yaml` is gitignored and generated by `scripts/render-secret.sh` from `$VALHEIM_SERVER_PASSWORD` in the workspace `.env`. Because `ws` sources `.env` before dispatch, `ws exec kubicvalheim bash scripts/render-secret.sh` works with no further setup.

The password must be at least 5 characters and **must not appear inside the server or world name**, compared **case-insensitively** — `render-secret.sh` lowercases both operands first, so "Vikings" is rejected against a server named "Shattered Vikings" exactly as "vikings" is. The rule runs in that direction only: the password cannot be a substring of the name.
